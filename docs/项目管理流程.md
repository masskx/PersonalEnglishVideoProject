# 项目管理流程

更新：2026-10-13。第一次使用双击根目录 [00-打开工作台.html](../00-打开工作台.html)。

首页“拿到成片，准备发布”是日常入口：选择作品，播放并保存 MP4，保存双封面，复制文案，再进入抖音、小红书或 B站投稿。平台登录和最后发布由用户完成。

四级作文、四级翻译、六级阅读的交付分别在 `outputs/cet4-writing-paragraph-v2/`、`outputs/cet4-translation-main-clause/`、`outputs/cet6-reading-location-paraphrase/`。
工作台从选题台账发现新栏目的 outputs 成片，根词系列继续读取注册表；完成后运行 `npm run project:inventory` 更新页面。发布材料按钮直接链接原文件，不是低清预览导出。

选题计划与复盘在页面后方折叠区。浏览器中的编辑仍须导出 JSON 备份；源计划在 `planning/content-plan.json`。网页计划不代替正式发布记录。

## 1. 找一条已经做好的视频

在管理页输入词根、单词或中文含义。每张卡片提供最终视频、竖封面、横封面、发布文案和本期资料入口。最终文件仍在 `outputs/<期名>/` 或 `outputs/<期名>发了/`。

每期目录统一分工：

| 文件 / 目录 | 用途 |
| --- | --- |
| `<期名>.mp4` | 当前最终视频 |
| `cover.png`、`cover-landscape.png` | 抖音竖封面与小红书横封面 |
| `publish-copy.md` | 主要发布文案；douyin-copy.md 保留为兼容副本 |
| `content-qa.md` | 人工核对词义、例句、词源与助记的记录 |
| `release.json` | 本地制作/发布状态 |
| `README.md` | 自动维护的本期导航与素材入口 |
| 三份 `*-report.json` | 原有媒体/封面验收记录；历史 input 路径不改写 |
| `review/` | 分镜、抽帧、对比图、历史说明 |
| `vertical/` | 抖音竖屏完整版、约 40 秒预告、复习卡（`npm run vertical:render`） |
| `xiaohongshu/` | 旧期的小红书图文卡（2026-10-14 起停用；小红书改发同一条短视频，见 `outputs/shorts/`） |

部分作品另有 `assets/`、`audio/`，是原有交付素材副本，继续保留。管理页的“视频与双封面成套”只表示文件存在，不能替代内容复核或证明已在平台发布。

## 2. 制作一条新内容

先确定内容、词义和例句，再建立项目配置、分镜与提示词。新内容仍按本项目 Skill 制作；这是后续实际生产步骤，本次整理没有开始新片。

内容 → 配音/绘图 → 草稿 → 画面与音频检查 → 最终视频/双封面/文案 → 内容核对 → 发布记录。

配音与图片先查看生成计划。命令只有带 `--generate` 才调用付费生成接口。完整说明见 [配音与绘图](制作说明-配音与绘图.md)。一条命令完成交付：`npm run replica:produce -- --project=<期名> --stage=deliver`。

## 3. 草稿和正式交付分开

```powershell
# 草稿：默认到 work/drafts/<期名>/draft.mp4
npm run replica:render -- --project=<期名> --draft

# 正式交付：解析实际存在的 outputs 目录
npm run replica:render -- --project=<期名>
```

当前脚本会找到已有的“发了”目录，不会因为默认路径没有后缀而创建第二份目录。若两种目录同时存在，会明确报错，先核对两份内容再处理。

正式渲染先写入 `work/render-staging/`，视频、双封面、文案及技术检查齐全后才更新交付目录，上一版放在 `work/delivery-backups/<期名>/`。中途失败的暂存文件留在工作区用于排查。

验收截图默认到该期 `review/stills/`。`work/` 是本机临时目录（草稿、暂存、试验、淘汰图），整个目录不进 git，也不作为发布文件来源。

## 4. 内容核对单单独填写

```powershell
npm run replica:content:qa -- --project=<期名>
```

已有检查单会保留，不会被普通执行重置为空表。只在明确要重建检查单时使用 `--force`。填写现代义、自然例句、词源来源、助记边界、核对人/日期，完成后再标记内容结论。

本次补齐了 rupt、mit-miss 缺失的检查单，均为待核对；其他 15 份原表原样保留。rupt 中“interrupt me，就是别打断我”缺少英文否定，下一次内容修订时应同步修正源稿、字幕和对应配音，重新导出，不应只改源码。

## 5. 更新本地状态

以下命令只维护本地记录和目录名，**不会上传或发布**。替换期名以及真实的平台、日期和链接；未知信息不编造。

```powershell
# 尚在制作
npm run replica:release -- --project=<期名> --status=draft

# 本地确认成片已批准
npm run replica:release -- --project=<期名> --status=approved

# 你确实已在平台发布之后，才补本地发布记录
npm run replica:release -- --project=<期名> --status=published --platform=douyin --published-at=<真实日期> --post-url=<真实链接>

# 更新管理页
npm run project:inventory
```

published 会保留或添加“发了”后缀；恢复 draft / approved 会去掉后缀。更新保留原有自定义字段，避免丢掉已有 QA 等信息。

目前 flect-flex、struct、tract 的文件夹写“发了”而 JSON 写 draft，rupt 的 JSON 写 approved。管理页统一显示“发布记录待核对”，不替你选择事实。确认哪一期实际已发后，用上面的命令补齐。

## 6. 每次收尾

双击 `刷新项目管理.cmd` 更新入口；或执行 `npm run project:inventory`。执行 `npm run project:check` 查看是否缺视频、封面、素材，是否存在重复目录或散落草稿。

`project:check` 不生成资源、不渲染、不发布；技术完整性与内容状态会分别报告。不要为了消除提示而把未核对内容标成通过。

## 删除与恢复

2026-10-13 整理时删除了旧归档（archive/）、全部试验与暂存（work/）、一次性审计与迁移记录、已停用的 Wan 图生视频与即梦/Seedream 脚本、interrupt 竖屏原型，以及没有任何一期引用的运行时素材。正式交付（outputs/）、各期实际引用的 public 素材、生成参考锚点和样片都保留。

需要找回旧文件时，用 git 历史恢复，例如 `git log --diff-filter=D --name-only -- work/` 查删除记录，再 `git checkout <提交>^ -- <路径>`。删除 `public/assets/` 前必须先确认没有任何分镜、配置或专用渲染器引用（`npm run project:check` 会检查运行时路径）。
